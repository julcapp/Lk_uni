# Техническое задание Lk_uni v1.0

## 1. Назначение

Lk_uni — универсальный модуль личного кабинета, регистрации, входа и управления пользовательской идентичностью для быстрого встраивания в разные проекты.

Модуль должен работать как самостоятельный сервис и как подключаемый блок для внешних систем:

- CRM;
- SaaS-сервисы;
- корпоративные порталы;
- Telegram/MAX/VK-боты;
- клиентские кабинеты;
- внутренние панели управления;
- проекты с программами лояльности.

## 2. Главный принцип

Lk_uni не должен быть жёстко привязан к одному проекту. Каждый внешний проект подключается через `project_id`, собственные настройки авторизации, брендинг, домены и набор разрешённых способов входа.

## 3. Базовая модель

Пользователь — единая сущность.

Email, телефон, MAX, Telegram, VK ID, SberID и другие каналы — это не отдельные пользователи, а связанные способы идентификации пользователя.

```text
User
  └── Identity
        ├── email
        ├── phone
        ├── max
        ├── telegram
        ├── vk
        └── sberid
```

## 4. Обязательные возможности v1.0

### 4.1. Регистрация

Система должна поддерживать регистрацию пользователя через:

- email;
- телефон;
- MAX;
- Telegram;
- VK ID;
- SberID;
- комбинированный сценарий: данные пользователя + подтверждение одним из каналов.

### 4.2. Подтверждение регистрации

Подтверждение регистрации выполняется через один из разрешённых каналов, заданных в настройках проекта.

Пример:

```yaml
required_verification:
  mode: one_of
  channels:
    - email
    - phone
    - max
```

Это означает: пользователь считается подтверждённым, если успешно прошёл любой один канал из списка.

Также должна быть возможность режима `all_of`, если проекту потребуется обязательное подтверждение сразу нескольких каналов.

### 4.3. Вход

Система должна поддерживать вход:

- по email;
- по телефону;
- через MAX;
- через Telegram;
- через VK ID;
- через SberID;
- через уже активную refresh-сессию.

### 4.4. Привязка внешних идентификаторов

После входа пользователь может привязать дополнительные способы входа:

- MAX;
- Telegram;
- VK ID;
- SberID;
- email;
- телефон.

Один внешний идентификатор не может быть привязан к нескольким пользователям в рамках одного проекта.

### 4.5. Проектные настройки

Для каждого проекта настраиваются:

- название проекта;
- публичный slug;
- домены;
- callback URL;
- разрешённые способы регистрации;
- разрешённые способы входа;
- обязательные способы подтверждения;
- брендовые цвета;
- логотип;
- текст пользовательского соглашения;
- политика обработки персональных данных;
- срок жизни кодов подтверждения;
- срок жизни сессий.

## 5. PostgreSQL

MySQL исключается из целевой архитектуры.

Основная база данных v1.0 — PostgreSQL.

Причины:

- лучше подходит для универсальной Identity Platform;
- строгие ограничения и индексы;
- `jsonb` для гибких проектных настроек;
- расширяемость под аудит, события, роли и permissions;
- удобная миграционная модель.

## 6. MAX

MAX реализуется как один из каналов:

- подтверждения регистрации;
- входа;
- привязки аккаунта;
- получения подтверждённого номера телефона через `request_contact`, если включено проектом.

MAX не является обязательным глобально. Обязательность MAX определяется настройками конкретного проекта.

## 7. Роли

Минимальные роли v1.0:

- `user` — обычный пользователь;
- `project_admin` — администратор проекта;
- `platform_admin` — администратор Lk_uni.

## 8. API

Сервис должен предоставлять REST API:

- `/api/projects/public/:slug`;
- `/api/auth/register`;
- `/api/auth/login`;
- `/api/auth/logout`;
- `/api/auth/refresh`;
- `/api/auth/me`;
- `/api/auth/verify/start`;
- `/api/auth/verify/confirm`;
- `/api/auth/oauth/:provider/start`;
- `/api/auth/oauth/:provider/callback`;
- `/api/auth/max/start`;
- `/api/auth/max/webhook`;
- `/api/users/me`;
- `/api/admin/projects`.

## 9. UI

Интерфейс должен включать:

- экран входа;
- экран регистрации;
- экран выбора способа подтверждения;
- экран подтверждения через MAX;
- экран привязки внешних аккаунтов;
- главную страницу личного кабинета;
- профиль пользователя;
- админ-панель настроек проекта;
- экран настройки каналов авторизации.

## 10. Нефункциональные требования

- HTTPS обязателен в production.
- Все токены и коды подтверждения хранятся в хешированном виде.
- Все попытки входа и подтверждения журналируются.
- Должны быть rate limits.
- Должна быть защита от повторного использования verification token.
- Должна быть защита от CSRF/state replay в OAuth и MAX deeplink flow.
- Должна быть поддержка нескольких проектов в одной инсталляции.

## 11. Критерии готовности v1.0

- PostgreSQL-схема создана.
- Регистрация работает минимум через email/phone.
- MAX flow описан и подготовлен к реализации.
- Вход работает через access/refresh token.
- Реализован `/me`.
- Реализована модель projects/settings.
- Подготовлен базовый UI.
- Документация по быстрому встраиванию готова.
