# Product Vision Lk_uni

## 1. Продуктовая идея

Lk_uni — не просто форма регистрации и входа.

Lk_uni проектируется как универсальная Identity Platform уровня Keycloak, Auth0 или Clerk, но с ориентацией на российскую экосистему и современные каналы идентификации.

Цель: один модуль авторизации, который можно быстро встроить в разные проекты без повторной разработки регистрации, входа, восстановления доступа и привязки внешних идентификаторов.

## 2. Позиционирование

```text
Lk_uni — универсальная Identity Platform для российских веб-проектов.
Один модуль, множество способов входа, единая архитектура и минимальное время интеграции.
```

## 3. Приоритетные каналы идентификации

Базовые:

- Email;
- телефон;
- MAX;
- Telegram;
- VK ID;
- SberID;
- Яндекс ID.

Возможные дополнительные:

- Госуслуги;
- корпоративный LDAP/AD;
- OAuth2/OIDC-провайдеры;
- Passkeys/WebAuthn;
- magic links.

## 4. Режимы использования

### 4.1. Demo Mode

Режим ознакомления с возможностями Lk_uni.

Назначение:

- отправить заказчику;
- показать партнёру;
- использовать на презентации;
- приложить к коммерческому предложению;
- быстро показать UX без развёртывания backend.

Формат:

```text
самораспаковывающийся ознакомительный пакет
```

Варианты реализации:

- Windows `.exe`, который распаковывает demo build и запускает локальный preview;
- `.zip` с `start.bat`;
- portable folder;
- Docker-free static build;
- GitHub Release artifact.

Ограничения Demo Mode:

- работает на моковых данных;
- не хранит реальные персональные данные;
- не подключается к production MAX/Telegram/VK;
- показывает только сценарии и интерфейс.

В Demo Mode допустимо показывать блок:

```text
Сервис: Демо-сервис Lk_uni
Данная форма применяется к сайту / проекту: ...
```

### 4.2. Embedded Mode

Основной режим для реальных проектов.

Lk_uni встраивается в продукт так, чтобы пользователь не видел техническое название Lk_uni.

Пользователь видит бренд конкретного проекта:

```text
Вход в CRM Атом
Вход в DevHub
Вход в У Тимоши
```

Варианты встраивания:

- React SDK;
- Web Component;
- iframe widget;
- redirect flow;
- REST API;
- backend-to-backend integration.

В Embedded Mode блок с названием Lk_uni и техническим проектом скрывается.

### 4.3. Standalone Mode

Режим требует отдельного обсуждения и дополнения.

Предварительная идея:

Lk_uni может работать как самостоятельный auth-домен:

```text
auth.company.ru
accounts.company.ru
login.company.ru
```

Потенциальные сценарии:

- единый вход для нескольких продуктов одной компании;
- кабинет пользователя для управления всеми привязанными сервисами;
- SSO между проектами;
- централизованное управление сессиями;
- централизованное восстановление доступа;
- управление согласиями;
- управление устройствами и audit log.

Вопросы для обсуждения:

- нужен ли единый глобальный профиль пользователя;
- как разделять пользователей между проектами;
- нужна ли организация/tenant model;
- нужен ли SSO;
- как реализовать брендирование в standalone-режиме;
- нужен ли пользовательский портал управления всеми подключениями.

## 5. Точки входа для разработчиков

### 5.1. React SDK

```jsx
<LkUniAuth projectSlug="utimoshi" />
```

### 5.2. Web Component

```html
<lk-uni-auth project-slug="utimoshi"></lk-uni-auth>
```

### 5.3. iframe Widget

```html
<iframe src="https://auth.example.ru/widget?project=utimoshi"></iframe>
```

### 5.4. Redirect Flow

```text
https://auth.example.ru/login?project=utimoshi&redirect_uri=https://utimoshi.ru/auth/callback
```

### 5.5. REST API

```http
POST /api/auth/register
POST /api/auth/login
POST /api/auth/verify/start
POST /api/auth/recovery/start
GET  /api/auth/me
```

### 5.6. Backend SDK

```js
const user = await lkUni.verifyAccessToken(token);
```

## 6. Рекомендации разработчикам

### 6.1. Не показывать пользователю техническое название Lk_uni

В production пользователь должен видеть бренд проекта, а не платформы авторизации.

### 6.2. Настраивать проект через конфигурацию

Форма не должна содержать поле `project`.

Проект определяется через:

- `projectSlug`;
- домен;
- redirect URL;
- API key;
- tenant config.

### 6.3. Использовать один из стандартных сценариев

Для большинства проектов рекомендуется начинать с Redirect Flow или React SDK.

### 6.4. Не писать собственную форму авторизации без необходимости

Форма должна собираться автоматически из `project_auth_settings`.

### 6.5. Сначала определить каналы

Перед интеграцией разработчик должен выбрать:

- способы регистрации;
- способы входа;
- способы восстановления;
- обязательность подтверждения;
- необходимость SSO.

## 7. Конструктор авторизации

Целевая функция продукта:

```text
разработчик включает провайдеры и правила — Lk_uni сам собирает форму
```

Пример:

```json
{
  "enabledProviders": ["email", "phone", "max", "telegram", "vk"],
  "requiredVerification": {
    "mode": "one_of",
    "channels": ["email", "phone", "max"]
  },
  "recoveryProviders": ["email", "phone", "max", "telegram"]
}
```

## 8. Вывод

Lk_uni развивается как инфраструктурный продукт.

Главная ценность — не отдельная форма, а готовая система идентификации, которую можно быстро подключать к новым проектам.
