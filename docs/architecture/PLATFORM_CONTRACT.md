# Контракт платформы Lk_uni

**Статус:** черновик для реализации PF-1  
**Область действия:** Platform Kernel, платформенные модули и подключаемые проекты

## 1. Назначение

Контракт определяет обязательства между ядром платформы, модулями и внешними проектами. Его цель — обеспечить предсказуемое подключение, обновление и отключение компонентов без нарушения целостности системы.

## 2. Участники

- **Platform Kernel** — загружает конфигурацию, проверяет совместимость, регистрирует и запускает модули.
- **Платформенный модуль** — предоставляет инфраструктурную возможность через публичный интерфейс.
- **Подключаемый проект** — использует сервисы Lk_uni, не получая доступа к внутренней реализации платформы.

## 3. Обязательный манифест модуля

Каждый модуль содержит файл `module.json`.

```json
{
  "schemaVersion": "1.0",
  "id": "auth",
  "name": "Ядро авторизации",
  "version": "0.1.0",
  "platformVersion": ">=0.1.0 <2.0.0",
  "entrypoint": "src/index.js",
  "dependencies": [],
  "provides": ["auth"],
  "permissions": [],
  "configuration": {
    "schema": "config.schema.json"
  }
}
```

### Обязательные поля

- `schemaVersion` — версия схемы манифеста;
- `id` — неизменяемый уникальный идентификатор;
- `name` — отображаемое название;
- `version` — версия модуля по Semantic Versioning;
- `platformVersion` — совместимые версии платформы;
- `entrypoint` — точка входа;
- `dependencies` — обязательные зависимости;
- `provides` — публикуемые возможности.

## 4. Жизненный цикл модуля

Kernel вызывает этапы строго в установленном порядке:

1. `discover` — обнаружение манифеста;
2. `validate` — проверка схемы и совместимости;
3. `configure` — получение проверенной конфигурации;
4. `register` — регистрация сервисов, маршрутов и обработчиков;
5. `start` — запуск фоновых процессов;
6. `ready` — подтверждение готовности;
7. `stop` — корректная остановка;
8. `dispose` — освобождение ресурсов.

Модуль не должен выполнять необратимые действия до успешного завершения `validate` и `configure`.

## 5. Регистрация сервисов

Модуль публикует сервисы через Service Registry. Имя сервиса должно включать пространство имён:

```text
lkuni.auth.sessions
lkuni.identity.profile
lkuni.audit.writer
```

Прямой импорт внутренней реализации другого модуля запрещён. Зависимости разрешаются через публичный контракт сервиса.

## 6. Конфигурация

Модуль получает только собственный раздел конфигурации и общие безопасные параметры платформы. Приоритет источников:

1. значения по умолчанию;
2. конфигурационный файл;
3. переменные среды;
4. секреты окружения;
5. разрешённые настройки проекта.

Секреты не должны попадать в журналы, диагностические ответы и клиентские API.

## 7. API и маршруты

Публичные маршруты модулей размещаются под версионированным пространством:

```text
/api/v1/auth
/api/v1/identity
/api/v1/projects
```

Каждый публичный маршрут обязан иметь:

- описание OpenAPI;
- правила аутентификации и авторизации;
- единый формат ошибок;
- тесты контракта;
- запись в журнале изменений при изменении поведения.

## 8. События

События публикуются в прошедшем времени и описывают уже состоявшийся факт:

```text
user.created.v1
user.logged-in.v1
password.changed.v1
session.revoked.v1
```

Полезная нагрузка события версионируется. Обработчик не должен считать порядок доставки гарантированным и обязан корректно переносить повторную доставку.

## 9. Разрешения

Модуль декларирует используемые разрешения. Формат:

```text
<область>.<ресурс>.<действие>
```

Примеры:

```text
platform.project.create
project.user.read
project.user.update
platform.audit.read
```

Доступ запрещён по умолчанию. Решение о доступе принимает единый Permission Framework.

## 10. Наблюдаемость

Модуль предоставляет:

- идентификатор и версию;
- состояние `healthy`, `degraded` или `unhealthy`;
- проверку готовности;
- структурированные журналы;
- диагностические метрики без конфиденциальных данных.

## 11. Обновление и совместимость

Перед активацией новой версии Kernel проверяет:

- совместимость с версией платформы;
- наличие обязательных зависимостей;
- допустимость миграций;
- совместимость публичных контрактов.

Несовместимое изменение требует увеличения основной версии модуля и документированной процедуры миграции.

## 12. Отключение и удаление

Модуль может быть отключён, если от него не зависят активные компоненты. Удаление данных выполняется только отдельной явной операцией и никогда не является автоматическим следствием отключения.

## 13. Контракт подключаемого проекта

Каждый проект регистрируется с уникальным идентификатором и явно указывает используемые сервисы, роли, разрешения и версии API.

```yaml
project:
  id: example-project
  name: Пример проекта
  apiVersion: v1

services:
  auth: true
  identity: true
  notifications: false
  audit: true

roles:
  - user
  - operator
  - administrator
```

Проект не может самостоятельно расширять свои полномочия или получать доступ к данным другого проекта.

## 14. Критерии соответствия

Компонент соответствует контракту, если:

- манифест проходит проверку схемы;
- жизненный цикл выполняется без скрытых побочных эффектов;
- зависимости разрешаются через Service Registry;
- публичные API и события версионированы;
- права проверяются централизованно;
- доступны Health Check и журналирование;
- документация и тесты актуальны.
