# ADR-0005. Изоляция данных подключённых проектов

## Статус

Принят.

## Контекст

Один экземпляр Lk_uni должен обслуживать несколько независимых коммерческих проектов. Ошибка авторизации или запрос без проектного контекста не должна приводить к доступу к данным другого проекта.

## Рассмотренные варианты

1. Разделять проекты только на уровне интерфейса.
2. Проверять `project_id` отдельно в каждом обработчике.
3. Ввести обязательный проектный контекст, централизованную авторизацию и защиту на нескольких уровнях.

## Решение

Принят вариант 3.

Каждая проектная операция выполняется в явно определённом проектном контексте. Доступ проверяется централизованной системой разрешений. Репозитории данных обязаны применять фильтрацию по проекту, а критические таблицы должны иметь ограничения целостности, исключающие смешение проектных данных.

Глобальные операции платформы доступны только через отдельный административный контур и не наследуют права администратора конкретного проекта.

## Последствия

Положительные:
- защита от межпроектного доступа;
- поддержка нескольких ролей и организаций;
- возможность последующего усиления изоляции через Row-Level Security или физическое разделение данных.

Отрицательные:
- проектный контекст должен передаваться через все слои;
- требуется больше негативных тестов;
- административные операции становятся отдельным контуром.

## Контроль соблюдения

Интеграционные тесты обязаны подтверждать, что пользователь проекта A не может читать или изменять данные проекта B даже при подмене идентификаторов в запросе.
