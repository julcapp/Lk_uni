# Фундамент платформы Lk_uni

## Статус

Принят как целевая архитектурная основа после выпуска DC1.

## Назначение

Фундамент платформы определяет минимальный набор инфраструктурных компонентов, на которых строятся Auth Core, Identity Service, реестр проектов, личные кабинеты и интеграционные интерфейсы.

DC1 остаётся приоритетом. Реализация перечисленных компонентов не должна задерживать демонстрационный выпуск.

## Рабочие пакеты PF-1

### PF-101. Ядро платформы

Отвечает за загрузку платформы, регистрацию модулей, управление жизненным циклом и остановку сервисов.

Критерии готовности:
- единая точка запуска;
- детерминированный порядок инициализации;
- корректная остановка;
- диагностический статус ядра.

### PF-102. Система модулей

Определяет единый манифест `module.json`, правила зависимостей, совместимость версий и жизненный цикл модулей.

Критерии готовности:
- проверка манифеста;
- обнаружение циклических зависимостей;
- отказ запуска несовместимого модуля;
- журналирование загрузки.

### PF-103. Реестр сервисов

Предоставляет модулям доступ к зарегистрированным платформенным сервисам через публичные интерфейсы без прямого импорта внутренних реализаций.

Критерии готовности:
- регистрация по уникальному идентификатору;
- получение сервиса по контракту;
- запрет дублирования;
- контроль жизненного цикла.

### PF-104. Система конфигурации

Объединяет значения по умолчанию, файлы окружения, переменные среды, секреты и настройки проекта.

Критерии готовности:
- схема и проверка конфигурации;
- безопасное сокрытие секретов;
- приоритет источников;
- диагностика отсутствующих параметров.

### PF-105. Шина событий

Обеспечивает внутрипроцессное взаимодействие модулей через версионированные события. Переход к внешнему брокеру сообщений допускается позднее без изменения предметных контрактов.

Критерии готовности:
- публикация и подписка;
- версия события;
- обработка ошибок подписчика;
- корреляционный идентификатор.

### PF-106. Система разрешений

Централизует проверки прав пользователя, роли, проекта и контекста запроса.

Критерии готовности:
- единый формат разрешений;
- запрет по умолчанию;
- проектная изоляция;
- запись результата проверки в аудит.

### PF-107. Система аудита

Фиксирует значимые действия пользователя, администратора, интеграции и платформы.

Минимальная запись содержит время, субъекта, проект, действие, объект, результат, источник и корреляционный идентификатор.

### PF-108. Система расширений

Определяет безопасное подключение дополнительных возможностей без изменения ядра.

На первом этапе создаётся только контракт. Marketplace и удалённая установка расширений не входят в PF-1.

## Зависимости

1. Ядро платформы загружает конфигурацию.
2. Система модулей определяет порядок загрузки.
3. Реестр сервисов публикует доступные контракты.
4. Система разрешений и аудит являются обязательными поперечными сервисами.
5. Шина событий используется для слабосвязанного взаимодействия.
6. Система расширений опирается на контракт модулей и реестр сервисов.

## Границы

Фундамент платформы не содержит CRM, торговли, вендинга, складского учёта, отраслевых процессов и иной предметной логики подключённых проектов.

## Порядок реализации

1. Завершить DC1.
2. Зафиксировать ADR.
3. Реализовать минимальное ядро и конфигурацию.
4. Добавить систему модулей и реестр сервисов.
5. Подключить разрешения и аудит.
6. Добавить события.
7. Подготовить контракт расширений.

## Определение готовности PF-1

PF-1 считается завершённым, когда:
- все компоненты имеют публичные контракты;
- зависимости и порядок запуска проверяются автоматически;
- проектная изоляция не может быть обойдена модулем;
- состояние компонентов доступно через диагностику;
- существуют модульные и интеграционные тесты;
- документация и ADR соответствуют реализации.
